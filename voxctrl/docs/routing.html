Routing & targets

Targets are named output destinations. Bindings tell voxctrl which target each hotkey should route to.

Delivery types

Type Mechanism Use for
inject wtype (Wayland) → xdotool (X11) → clipboard+Ctrl+V fallback; PowerShell clipboard paste on Windows Default dictation into focused window
clipboard System clipboard write only — no paste Copy for manual paste
file append or write, optional prefix & ISO timestamp Voice journal, meeting notes
exec shell command, transcript passed as argument CLI agents, one-shot commands
http HTTP POST, JSON body {"text": "..."} Webhooks, REST APIs
webhook HTTP POST signed with HMAC-SHA256 (X-VoxCtrl-Signature header) Authenticated webhooks, n8n, Zapier
socket Unix domain socket or TCP, newline-terminated Remote or containerised agents
pipe Named FIFO write Persistent agent processes
dbus text_injected signal on ai.voxctrl.Dictation Waybar, Rofi, desktop automation
mcp Enqueues response to a pending transcribe_voice MCP tool call MCP client integrations
speak Local TTS playback, no MCP/server required Hands-free voice replies
command Voice command router — "VoxCtrl <target name> <text>" routes to any other target by its spoken name One keybind for every destination
chat Turn-by-turn conversation with an OpenAI-compatible /v1/chat/completions endpoint; replies spoken, injected, or copied Voice front end for local LLMs (Ollama, llama.cpp, LM Studio, vLLM)

Voice command routing (command)

The command target — new in v0.3.6 — routes dictated text to other targets dynamically, based on what you say. Bind one hotkey to a target with delivery = "command", then call any configured target by name with the "VoxCtrl" keyword:

[[target]]
id       = "cmd_router"
label    = "Voice Command Router"
delivery = "command"

Say "VoxCtrl write to my notes. This is a great day." and the payload "This is a great day." is delivered to your Notes target. How it resolves:

  • Trigger keyword — listens for "VoxCtrl", case-insensitively, in any of its spoken shapes: VoxCtrl, voxctrl, vox ctrl, vox-ctrl, with optional trailing punctuation (VoxCtrl:).
  • Target resolution — the spoken name is matched against every configured target's id and label, case-insensitively. Longer names take precedence, so "Personal Notes" is matched before "Notes".
  • Conversational lead-ins — natural phrases between the keyword and the target name are understood: "VoxCtrl send this to my notes…", "VoxCtrl add this to my personal notes…", "VoxCtrl put this into my Notes: hello".
  • Payload extraction — transition punctuation (. : , ;) and connector words ("saying", "that", "with text") are stripped, and the remaining text is routed to the matched target with that target's own delivery and processing settings.
  • Confirmation overlay — a purple/indigo ⚡ command pill appears over your screen showing the matched target name and a payload summary, so you know the command was picked up. Configurable duration (default 3s) via ui.command_overlay_duration_secs; toggle with ui.show_command_overlay. See Overlays.
  • Auto-trigger detection — dictating with the "VoxCtrl" keyword activates voice command routing even when the active hotkey's target is plain inject — you don't have to be on the command binding for a spoken command to work.
  • Fallback — if no "VoxCtrl" keyword is spoken, or no target matches, the text is injected into the focused window exactly like the inject target. Nothing is dropped.

Conversational LLM (chat)

The chat target sends each dictation as a turn in an ongoing conversation to an OpenAI-compatible /v1/chat/completions endpoint — Ollama, llama.cpp, LM Studio, vLLM, or a remote provider — and surfaces the model's reply. Unlike http, it reads the response and remembers the exchange, so the model keeps context across turns.

[[target]]
id       = "hermes"
label    = "Hermes"
delivery = "chat"
chat_url = "http://localhost:8080"          # /v1 suffix optional
chat_model = "hermes-4-14b"
chat_system_prompt = "You are a concise voice assistant."
chat_reply_mode = "speak"                    # speak | inject | clipboard | none
chat_max_history = 20                        # messages per turn; 0 = whole conversation
chat_reset_phrase = "new conversation"       # optional; clears history instead of asking
  • Reply handling — speak reads the reply aloud via TTS; inject types it into the focused window; clipboard copies it; none runs the conversation silently.
  • Conversation lifetime — history is held in memory only, keyed by target id, and survives saving settings. It is cleared by the spoken reset phrase, the Reset conversation button in the target editor, or restarting voxctrl. It is never written to disk.
  • Failure behaviour — a failed, timed-out, or empty completion rolls the unanswered turn back so it is not resent on the next dictation.
  • Optional fields — chat_api_key (sent as a Bearer token) and chat_timeout_secs (default 120; local models can be slow to first token). Press Fetch models in the target editor to list the server's model ids.

Per-target processing

Each target's [target.processing] block can override the global post-processing settings. All fields are optional (null inherits the global config):

  • remove_fillers — strip filler words (um, uh, hmm, er, ah, ugh, mhm)
  • spoken_punctuation — convert spoken punctuation ("period" → ., "comma" → ,)
  • auto_format_lists — convert spoken ordinals into a numbered list
  • apply_snippets — expand custom shorthand snippets into full text
  • code_mode — camelCase / spoken-operator formatting for dictating code
  • quiet_mode — suppress overlay/sound feedback for this target
  • atspi_context — use AT-SPI2 to read surrounding context for this target
  • noise_suppression — enable/disable noise suppression for this target
ⓘ LLM rewriting (openai_enabled, openai_model, openai_mode, openai_prompt, openai_system_prompt) is configured per hotkey binding in bindings.toml, not per target — so the same target can be reached by different bindings using different rewrite styles. The model is served over the OpenAI API; legacy ollama_* field names are still accepted as aliases.
! Agent targets (exec, pipe, socket) should almost always use remove_fillers = true and spoken_punctuation = false. Rewriting alters command semantics.

Common patterns

Agent command pipe

Send voice commands to a CLI agent via FIFO (pipe_path). Strip fillers so the agent gets clean input. Use response_pipe to stream replies back as TTS.

Voice journal

Append timestamped entries to a markdown file with delivery = "file", file_prefix, and file_timestamp = true. Apply an LLM rewrite on the triggering binding to format each utterance as a concise note.

Shell command execution

Use delivery = "exec" with a command template. The transcript is passed as an argument to the command.

TCP or Unix socket to remote agent

Forward transcripts to a socket for distributed or containerised setups. Set socket_host and socket_port for TCP, or socket_unix for a Unix domain socket.

HTTP / webhook delivery

Use delivery = "http" for a simple JSON POST (http_url, http_method, optional http_headers / http_json_template), or delivery = "webhook" with webhook_url and webhook_secret to attach an HMAC-SHA256 X-VoxCtrl-Signature header for authenticated endpoints.

Multi-target routing

A binding's target_ids array can list multiple targets — voxctrl delivers to each sequentially in order after a single recording session (e.g. inject into the focused window, then log to a file).

One keybind, every destination

Bind a single hotkey to a delivery = "command" target and address every other target by voice: "VoxCtrl write to my notes…", "VoxCtrl clipboard…", "VoxCtrl send this to Hermes…". Anything without the keyword is injected as normal dictation, so the command router can safely be your default binding.

Config file locations

  • ~/.config/voxctrl/config.json — global settings (managed by Settings UI)
  • ~/.config/voxctrl/targets.toml — output target definitions
  • ~/.config/voxctrl/bindings.toml — hotkey → target bindings
ⓘ All three config files are hot-reloaded on save — no restart required.
