INPUT & ROUTING / HOTKEYS

Hotkeys & gestures

On Linux, voxctrl receives global shortcuts through the XDG desktop portal — your desktop owns the key grab and tells voxctrl only that its own shortcut fired, so voxctrl never reads your keyboard. On Windows, Win32 low-level keyboard hooks are used.

How shortcuts are delivered

voxctrl talks to the org.freedesktop.portal.GlobalShortcuts portal over D-Bus. It registers your configured keys as a preferred trigger; your desktop decides what to actually bind and sends Activated/Deactivated events when the shortcut is pressed and released. That is the entire data flow — voxctrl never sees what you type in your browser, terminal, or password manager, because it is never given the data.

  • No permission setup. Nothing to install, no group to join, no udev rule to write, no logout. Earlier versions read /dev/input/event* directly and needed a broad udev rule; upgrading removes that rule, narrowing access rather than leaving it wide open.
  • Supported desktops — KDE Plasma 5.27+, GNOME 48+, and Hyprland. On KDE, a confirmed upstream bug (#483639) registers portal shortcuts unticked — enable them once under System Settings → Shortcuts; the Hotkeys tab shows a standing notice with an Open Shortcut Settings button.
  • Linux Mint (Cinnamon / MATE) — no portal yet, so voxctrl offers a one-click "Add Mint Native Shortcut" that binds a Mint system shortcut to voxctrl's ai.voxctrl.Dictation D-Bus interface. Zero special permissions.
  • evdev fallback — only used when no portal is available and your system already allows the process to read input devices; voxctrl never grants itself that access, and the Hotkeys tab says plainly which mode is in use.

What can be a shortcut

A portal accelerator is any number of modifiers plus exactly one regular key — Super+Space, Ctrl+Alt+D, and F5 are all fine. Two shapes cannot be bound by any desktop: modifiers alone (a lone Super, or Ctrl+Shift with nothing else) and two regular keys (A+B). The key recorder in Settings → Hotkeys refuses these while you record and says why, rather than saving something that silently never fires. On the evdev fallback and on Windows a bare modifier genuinely works, and the recorder accepts it there with a note.

Default bindings

Gesture Keys Action
Hold-to-talk Super + Space Hold while speaking, release to deliver
Toggle-to-talk Ctrl + Super + Space Tap to start, tap again to stop
Double-tap Alt + Z Two quick taps to start, two to stop

All configurable in Settings → Hotkeys or directly in ~/.config/voxctrl/bindings.toml. Each gesture can be disabled without deleting it.

Gesture modes

Hold

Most predictable. Press, speak, release. Mic state is unambiguous — visible in the overlay. The hold_threshold_ms field (default 200ms) sets the minimum hold duration before a recording start is registered, preventing accidental triggers.

Toggle

Hands-free. Tap once to start, tap again to stop. The RMS noise gate also stops recording on silence if configured.

Double-tap

Reuses a combo you already have without colliding with normal usage. Recording starts on the second press within the tap_ms window (default 300ms). A first tap held longer than 600ms is not a tap at all, so ordinary use of the keys never primes a phantom double-tap.

Double-tap-hold

Double-tap and keep the key held down on the second tap to start recording; release the key to stop. Enforces hold_threshold_ms on the second press to distinguish it from a standard double-tap. Releasing always stops the recording; a 2-minute safety timeout is a backstop for a release that never arrives. double_tap and double_tap_hold on the same keys are a supported pairing, not a conflict — a quick double-tap runs one, double-tap-and-hold runs the other.

ⓘ The chord gesture has been removed — it could not be expressed as a portal system shortcut. Existing chord bindings keep working: on load they are converted to hold using their base keys, and the obsolete subkey field is dropped the next time bindings are saved. Nothing needs editing by hand.

Staggered release tolerance

For hold and double_tap_hold gestures on multi-key combos, a 50ms grace window covers fingers that don't lift off every key at the same instant — recording stops cleanly whether the remaining keys come up quickly, late, or their key-up events are swallowed by the compositor.

Conflict detection

The Settings UI checks for collisions as you record new keys:

  • Exact duplicate — both gestures fire simultaneously
  • Superset shadowing — if one binding's keys are a subset of another's (e.g. Super+Space vs Ctrl+Super+Space), only the longer, more specific combo fires
  • Double-tap overlap — double-tap key appears in a hold/toggle combo
  • Bare single key — non-modifier key alone intercepts every press

Recording new bindings

Press the Bind button next to a key field. The button turns orange and shows "Recording…". Press your keys. The display updates live as keys are held. Release — binding captured.

ⓘ The recorder validates against the same accelerator rule the portal enforces, nudges you while you are holding modifiers with no regular key yet, and shows the accelerator your desktop will receive (e.g. LOGO+space) once the combination is valid. A refused capture leaves your existing shortcut untouched, and re-binding never fires the old shortcut mid-recording.

Configuration

The full schema for ~/.config/voxctrl/bindings.toml with one binding per gesture type:

[[binding]]
id        = "dictate_hold"
label     = "Dictate (Hold)"
keys      = ["KEY_LEFTMETA", "KEY_SPACE"]
gesture   = "hold"
target_ids = ["default"]
hold_threshold_ms = 200

[[binding]]
id        = "agent_command"
label     = "Agent (Double-tap)"
keys      = ["KEY_LEFTCTRL"]
gesture   = "double_tap"
target_ids = ["hermes"]
tap_ms    = 250

[[binding]]
id        = "voice_command"
label     = "Voice Command Router"
keys      = ["KEY_LEFTMETA", "KEY_C"]
gesture   = "toggle"
target_ids = ["cmd_router"]

Other fields: target_id (legacy singular target, resolved when target_ids is empty) and disabled (default false, disables a binding without removing it). LLM rewriting per binding is configured with the openai_enabled, openai_model, openai_mode, openai_prompt, and openai_system_prompt fields — the legacy ollama_* field names are still accepted as aliases.

Supported gesture values

Value Description
hold Record while key is held; stop on release
toggle First press starts; second press stops
double_tap Two presses within tap_ms window to activate
double_tap_hold Double-tap and keep held on the second press to start; release to stop
chord (removed) Loaded as hold automatically; the subkey field is ignored and dropped on the next save
